# M0-C Owner login and a safe dashboard: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Only a logged-in human reaches the dashboard. Every command checks that human's role, and the risky ones also need the approval PIN. Every command is audited under the human's own id. Text written by agents can never run or pass for HQ's own text in the owner's browser.

**Architecture:**
- **Store.** The company store gains a credentials table: password and PIN as slow salted hashes, and the TOTP seed encrypted with a key file kept outside the database.
- **Login.** A new `OwnerAuth` serves login and first-run enrollment over HTTP and keeps cookie sessions in memory. It replaces the per-start browser token on the WebSocket upgrade.
- **Commands.** Each dashboard command gets a declaration: the lowest role that may run it, when it needs the PIN, and whether a remote session may run it. One dispatcher enforces the declaration and writes the audit row.
- **Browser.** Every HTTP response carries a strict Content Security Policy. The UI shows agent text only through two components that label it with its author and never interpret it as HTML.

**Tech stack:** Node ≥ 22.13 (`node:crypto`: `scrypt`, `createHmac`, AES-256-GCM, `randomBytes`), TypeScript, React 18 (`react-dom/server` for component tests), the existing `ws`. No new packages.

**Spec:** `docs/superpowers/specs/2026-11-09-agentic-company-m0-m1-design.md`:
- M0.7 (login, PIN, escaping, sanitised markdown, CSP).
- M0.14, third and fourth bullets (per-command human-role check; owner-started permission changes are direct, PIN-confirmed and audited).
- Surfaces S5 and S10 (§2b), the owner-side risks under §2b, and §9 items 2 and 6.

Requirements: `docs/security/threat-model-m0.md` §3.2, SR-C-01 to SR-C-19. Order and carry-forward: `docs/superpowers/plans/2026-11-11-m0-foundations-overview.md`.

## Where this plan reads the spec narrowly (for the reviewer)

- **Supervisors exist in the store, not in the UI.** SR-C-04 and SR-C-09 need a Supervisor session to test against.
  - `HumanAccounts` can enroll any human, and the tests create a supervisor that way.
  - Adding supervisors from the dashboard, and what they may do beyond pausing, is M1.11.
  - In M0-C a supervisor may run one command, `stopAgent` (the pause direction, §9 item 2), and sees the reduced view in Task 4.
- **The PIN travels with the command it confirms.** SR-C-05 asks that a PIN confirm "one named action, once, within a short time".
  - The dispatcher checks a PIN sent inside the command message, for that message only, and keeps nothing a second command could reuse. So no "confirmation" outlives the action.
  - The test checks that a PIN sent with X authorises nothing for a following Y, and that resending X's message is checked again and counts toward the lock.
- **Terminal keystrokes are audited collapsed.** SR-C-07 asks for a row per command. `sendTerminalInput` and `resizeTerminal` arrive once per keystroke or resize.
  - They write one `dashboard.terminal` row per session, agent and minute, with a count and never the typed text, which can hold secrets (anti-goal §4).
  - Every other command writes one row per call.
- **"Remote" means not provably local.** HQ listens on 127.0.0.1, so a phone reaches it through a local proxy (`tailscale serve`). The socket address cannot tell remote from local.
  - A session is local only when all three hold: the socket address is loopback; the request carries no `X-Forwarded-For`, `Forwarded` or `Tailscale-*` header; and `Host` is `127.0.0.1`, `localhost` or `[::1]`.
  - Anything else is remote. Separate listeners (SR-G-01) make this exact in M0-G.
- **Lockouts are per source, and the source comes from the proxy when there is one.** For a loopback socket with `X-Forwarded-For`, the source is that header's first address; otherwise it is the socket address.
  - A local process could vary the header to dodge the per-source lock. That process already runs on the owner's host, which §2b accepts. The PIN lock (per human) and the TOTP replay check do not depend on the source.
- **SR-C-10's "every agent-written field" is met in two layers.**
  1. A source scan fails the build if `src/` contains any way to turn a string into markup or code: `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `srcdoc`, `eval(`, `new Function`, or an `href={…}` that does not go through `safeHref`.
  2. A real-browser test renders the components that show agent text (`AgentText`, `AgentMarkdown` and the system items) with a payload set.
  - React escapes everything else by construction, and the scan proves nothing bypasses React.
- **SR-C-11's Owner Briefing does not exist until M1.** M0-C builds the sanitising renderer (`AgentMarkdown`) and uses it for action-item details, the agent-written markdown that exists today. M1's briefing uses the same component.
- **SR-C-15 is partial; the threat model marks it (proposed).**
  - HQ stops setting `BROWSER` for agent sessions, which is the test the threat model names.
  - The opener sbx installs (`/usr/local/bin/xdg-open`) stays callable by name inside the sandbox, and HQ cannot remove it.
  - ADR 0007 records that, and M0-G checks on the Linux host whether `sbx` can turn it off.
  - Cost to the owner: an agent's login link no longer opens by itself. It is still printed in the terminal, where it is clickable.
- **SR-C-14 (proposed) is built.** It is cheap and costs nothing visible: links in agent output are still matched by the web-links addon.
- **Real-browser tests need Chrome or Edge.** `server/testing/browser.ts` finds one (`HQ_TEST_BROWSER`, then the usual install paths and `PATH`).
  - GitHub's Ubuntu, macOS and Windows runners all have Chrome, so these tests run in CI.
  - With no browser they skip with a message naming `HQ_TEST_BROWSER`. Each such test also asserts something without the browser (headers present, markup escaped), so a skip never leaves the requirement untested.
- **The CSP applies where HQ serves the UI.** Under `pnpm dev:hq` the page comes from Vite, which needs inline scripts for hot reload. The development page therefore runs without the CSP, and the README says so.

## Global constraints

- Keep the existing stack (spec §7). No new packages.
- Anti-goal §4: a secret value never enters "a log, an alert or the audit trail". That covers passwords, PINs, TOTP codes and seeds, session ids, setup codes, and secret values typed into the dashboard.
- Anti-goal §4: existing capabilities must not regress. On Ubuntu, macOS and Windows these must pass: `pnpm typecheck`, `pnpm test`, `pnpm build`, `npx tsx scripts/session-backend-test.ts` and `scripts/smoke-test.mjs`.
- Every enforcement test follows the threat model's rules (§3 preamble):
  - the refusal is checked;
  - its audit row is checked, with the actor being the authenticated human, or `{ kind: "anonymous" }` before login;
  - the targeted state is read back unchanged;
  - the title is `SR-C-nn [T-…] …`.
- Times come from the injected `Clock` (M0-A): session lifetimes, lockouts, TOTP steps and rate limits.
- No product name in code (M0-H). The TOTP issuer label is `HQ`.
- `.github/`, `CLAUDE.md` and `.claude/settings.json` are not touched. CI runs `pnpm test` already, so the new test files need no workflow change.

## Values this plan fixes

| What | Value |
|---|---|
| Password | 12 to 256 characters |
| PIN | 6 to 12 digits |
| Hash | `scrypt`, N = 2^15, r = 8, p = 1, 32-byte key, 16-byte salt, `maxmem` 64 MiB. Stored as `scrypt$15$8$1$<salt>$<hash>` (base64url); compared with `timingSafeEqual` |
| TOTP | RFC 6238: SHA-1, 6 digits, 30 s step, 20-byte seed, base32. The previous, current and next steps are accepted. A step at or below the last one used is refused |
| Seed encryption | AES-256-GCM, 12-byte IV. Stored as `v1:<iv>:<tag>:<ciphertext>` (base64url). Key: 32 random bytes in `<company home>/owner.key`, mode 0600, created at enrollment |
| Setup code | 16 random bytes, base64url, in `<company home>/owner-setup.txt`, mode 0600. Written at startup while no owner is enrolled, deleted when enrollment completes |
| Session | 32 random bytes, base64url. Kept in memory under its SHA-256. Cookie `hq_session` with `HttpOnly; SameSite=Strict; Path=/`, plus `Secure` when the request came over HTTPS (TLS, or `X-Forwarded-Proto: https` from loopback). Idle limit 30 min, absolute limit 12 h |
| Login lock | Per source: 5 failures within 15 min lock that source for 15 min |
| PIN lock | Per human: 5 wrong PINs lock the PIN step for 15 min |
| WebSocket rate | Per connection: a bucket of 100 messages refilling at 50/s. Over it, the message is dropped and one `dashboard.rate-limited` row is written per minute |
| Allowed origins | Today's loopback list, plus a comma-separated `HQ_DASHBOARD_ORIGINS` (M0-G sets it for the Tailscale name) |

**Files:**

- Modify: `server/commands.ts` (every command becomes a `CommandSpec`; `DASHBOARD_ACTOR` is removed), `server/http.ts` (`onClient` calls `dispatch`), `server/company/agents.ts` (remove `DASHBOARD_ACTOR`), `src/data/source.ts` (`command.result` event), `server/mcp.test.ts`

**Interfaces:**
- Consumes: `HumanRole` (Task 1), `OwnerAuth` and `DashboardSession` (Task 2).
- `interface CommandCtx { actor: { kind: "human"; id: string }; role: HumanRole; remote: boolean; sessionId: string }`.
- `interface CommandSpec`:
  - `role: HumanRole` (lowest role allowed);
  - `pin?: boolean | ((args: unknown[]) => boolean)`;
  - `localOnly?: true`;
  - `target?: (args: unknown[]) => string | null` (an agent id or a name, never a value);
  - `audit?: "per-call" | "collapsed"` (default `"per-call"`);
  - `run: (ctx: CommandCtx, ...args: unknown[]) => unknown`.
- `makeCommands(...)` returns `Record<string, CommandSpec>`.
- Message format: `{ cmd, args, pin?, id? }`. The reply goes only to the sending socket:
  - `{ type: "command.result"; id: string; ok: boolean; error?: "unknown" | "forbidden" | "remote" | "pin-required" | "pin-wrong" | "pin-locked" | "rate-limited" | "failed" }`.
- `dispatch(spec, ctx, msg)` order:
  1. A command missing from the table, or one with no `role`, is refused.
  2. Role check.
  3. `localOnly` against `ctx.remote`.
  4. PIN rule, then the PIN lock, then `verifyPin`.
  5. `run`.
  - Each step that refuses writes the row and stops.
  - The row is `dashboard.command` with `target`, `data` = `{ cmd, outcome: "ok" | "refused" | "failed", reason? }`, and actor `ctx.actor`.
  - A failure's message is never copied into the row, the reply or the activity feed (SR-C-17). `failed` is the whole report.
- The command table (role is `owner` unless a row says otherwise). PIN-needing commands are the approve, grant or relax direction (§9 item 2):

| Command | Rule |
|---|---|
| `stopAgent` | `supervisor` |
| `sendTerminalInput`, `resizeTerminal` | `localOnly`, collapsed audit |
| `openShell`, `openHostShell`, `openWorkspace`, `openEnvFile`, `runSetupFix` | `localOnly` |
| `addAgent`, `removeAgent`, `completeWelcome`, `setSecret`, `setProxy`, `addMcp`, `authMcp`, `setAgentMcp` | PIN |
| `updateAgent` | PIN when the patch has `mode`, `cli`, `workspacePath`, `roleMd` or `skills` |
| `updateSandbox` | PIN when the patch has `allow` or `deny` |
| `updateWorkflow` | PIN when `merge.by` changes |
| `answerApproval` | PIN when the decision is `allow` |
| `resolveAccess` | PIN when the decision is `agent` or `everyone` |
| All other commands | `owner`, no PIN |

- `OwnerAuth.checkPin(humanId: string, pin: string): Promise<"ok" | "wrong" | "locked">`. It keeps the lock per human (5 wrong → 15 min), calls `HumanAccounts.verifyPin`, and writes `auth.pin-locked` when the lock starts.
- WebSocket rate: the per-connection bucket from the values table. It counts every message, terminal input included.

  - `SR-C-04 [T-S5.2 T-S5.7] a supervisor is refused every owner command, and audited`:
    - each owner-only command from a supervisor session gets `forbidden`;
    - one row per call, actor = the supervisor;
