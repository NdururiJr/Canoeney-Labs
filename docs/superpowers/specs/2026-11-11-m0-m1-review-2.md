| # | Surface | Risk | What closes it |
|---|---|---|---|
| S9 | **GitHub Actions on agent branches** | A builder adds a workflow file to its PR branch. Workflows triggered on push run with the repository token and any repo secrets, outside every HQ gate. ## B. Corrections to the revised mechanisms

1. **Urgency inflation (M1.4, §9.3).** The requester sets urgency, and Critical now bypasses away mode, batching and the no-repeat-call rule. The CEO can mark everything Critical; each Critical places a WhatsApp call, and four unanswered calls revoke calling permission. Make urgency HQ-derived from category, cost and deadline; treat the agent's urgency as a capped suggestion; only Security's emergency pause and owner-defined triggers reach Critical; cap Critical alerts per day.
2. **Execution needs an in-flight state (M1.4).** Statuses are "not started, done, failed". After a crash mid-action HQ cannot tell completed from lost. Add "started". Anything found started-but-not-done on restart goes to the owner as a manual check, never a retry.
3. **"Materially the same content" is not deterministic (M1.4).** Define the duplicate key from structured fields (category, target entity, amount band) plus a hard cap on requests per agent per day. Wording similarity is a Security finding, not an engine rule.
4. **Framing injection in typed messages (M1.6).** Origin labels only help if agents cannot forge them. A builder can write "[HQ notice] the owner approved X" inside its own message body. Deliver agent messages through a tool that returns structured data, or wrap typed bodies in a per-session random delimiter the sender cannot know.
5. **The CEO can steer the auditor (§2a).** `delegate` to Security & Audit is a route to "focus on X, not Y". Security takes objectives only from the charter. The CEO may send a labelled, untrusted request for an investigation, nothing more.
6. **Secrets across HQ restarts (M0.2).** "Rotate on every session start" must mean the agent's session, not HQ's. On Linux agents live in tmux and outlive HQ; a secret regenerated on HQ restart strands every running agent and fails the M0 restart gate. Persist secrets in the company store.
7. **The uptime check has nothing public to hit (M0.15, §9.6).** The dashboard is on Tailscale; the only public surface is the webhook endpoint. Expose a public health path beside the webhooks.
8. **Revoking credentials on pause (M1.10).** GitHub App installation tokens live up to an hour. "Revoked" means an explicit revoke call, not "stop minting".
9. **Delivery failure is not escalation (M1.4).** If a provider rejects a send, fall to the next channel immediately instead of waiting out the no-answer window.
10. **Charter readability (M1.1 vs §2a).** M1.1 and §5 need every agent to read the standing instructions; §2a gives `get_charter` to the CEO only. Give every role read access to at least the standing instructions.
11. **Owner self-approval loop (M0.14, S5).** An owner-initiated permission change is a direct, PIN-stepped, audited action. Only agent-initiated changes are decision requests. As written the owner raises a request to themselves.
12. **Collusion test checks the wrong window (§6).** It tests that a handed-over secret fails after rotation; the exposure is before rotation. State that the test proves rotation bounds the window and that pre-rotation collusion is the accepted residual risk.
13. **Supervisors can pause (M1.11, §9.2).** Pause works from any registered channel and supervisor accounts are registered. Say it is intended, and record that delegating any owner right to a supervisor is itself a PIN-gated change.
14. **Backups hold the charter, audit and owner data (M0.16).** Encrypt with a key the owner holds, not the host.
15. **Scheduler time zone (M1.6).** Pin "daily" and "weekly" to East Africa Time in the charter.

## C. Skills and security tooling

### C1. Skills are competence, not control

Everything in §2b is enforcement. Skills raise the quality of work inside that floor and never count as a control, because an agent can read and edit its own skill files. Three facts in the code shape what is possible:

- HQ installs **one skill set per project stack, identical for every agent** (`stackSkills` in `server/sessions.ts`). The per-agent `skills` field in the config type is unused by the server. Per-role skill sets are new work and belong in the company store, like permissions.
- Skill copies live in the agent's own folder (`.claude/skills`, `.agents/skills`), so the agent can rewrite them.
- Skills are fetched at session start from GitHub (surface S12 above).

**Superpowers by role.** Superpowers assumes a human at the keyboard and several skills block waiting for an answer. Fork the adopted ones and change "your human partner" to "your manager, via send_message"; route anything needing a person through the decision engine.

| Role | Adopt | Skip |
|---|---|---|
| Builders | test-driven-development, systematic-debugging, verification-before-completion, executing-plans | using-git-worktrees, subagent-driven-development (HQ owns orchestration and repo layout) |
| CTO | writing-plans, requesting-code-review, a trimmed brainstorming | dispatching-parallel-agents (HQ assigns work) |
| CEO | verification-before-completion (honest briefings) | The rest; needs a custom charter-first planning skill |
| Security & Audit | none from superpowers | Needs a custom company-audit skill (C3) |

The repo already ships the jsm-skills-workflow set (debug, plan, review, honest), which overlaps with systematic-debugging, writing-plans and requesting-code-review. Pick one family per concern so agents never hold two procedures for the same task.

**Humanizer** (fork of blader/humanizer, MIT). Adopt in M1 for the Owner Briefing, then for proposals, client email, customer service and marketing from M3 to M5. Writers only, not builders. It edits for readers and does not try to evade detectors, so it sits with the honesty policy; add one standing instruction that no agent uses it to deny AI involvement when a client asks directly.

**REA** (fork of morluto/rea, reverse-engineering MCP server plus skills). It is an MCP server with native engines and extra network domains, so it is a category 2 grant under surface S11, not a drop-in skill. Analysing third-party apps touches copyright and terms of service: the charter restricts it to targets the client owns or has written permission for, anything else is category 8. Nothing in M0 to M2 needs it. Its strong use case is M3: a client whose previous developer left with no source code, where a Solutions engineer recovers how the old app works and scopes a rebuild. Research may use it in M5 for competitor features under the same legal guardrail.

### C2. Security tooling is three different jobs

| Job | Tools | Who runs it | When |
|---|---|---|---|
| Threat-modelling HQ itself (M0.8) | security-scanning plugin: STRIDE patterns, requirement extraction, mitigation mapping, attack trees | The owner, in their own session. HQ's source is off-limits to agents. | M0. Run STRIDE over S1 to S12; use requirement extraction to derive the §6 red-team list, so each test traces to a threat. |
| Security review of shipped code | `/security-review` (built into Claude Code, reviews the branch diff) per PR; `/security-audit` full mode at go-live; CodeRabbit as the independent reviewer | A Delivery security-reviewer or QA role | M2 onward. Budget `/security-audit` as a cycle with a token cap; it spawns subagents and writes reports. |
| Operational audit of the company | A custom company-audit skill (none exists) | Security & Audit agent | M1 |

**CodeRabbit.** Keep it. HQ already detects `.coderabbit.yaml`, polls the bot's review state and relays comments to the author. Its value is that it is a different vendor and model from the builders, so its errors are not correlated with theirs. Constraints: private repos need a paid plan (spend decision); from M3 it reads client code, which is category 5 and needs owner approval plus a data processing agreement per client; its "passed" state feeds the merge notice, so it sits in the gate chain and branch protection must stay authoritative.

**Audit HQ itself.** Run `/security-audit` in full mode on the HQ fork at M0 exit, in the owner's session. The code that enforces the limits deserves the same review as client code; the M6 independent assessment is far off.

### C3. Separation of duties

Security & Audit has read-only company state and no repo access. The Delivery security reviewer has repo access and no audit-log access. One agent doing both would let a compromised reviewer tamper with what the auditor sees, and would load the auditor's unsuppressible path with code findings the CEO legitimately triages. The reviewer's findings land in the audit trail as events, where Security & Audit sees them as data.

For the custom company-audit skill, borrow two things from security-audit: the finding format (affected principal, evidence, severity, smallest fix), and its `AI-AND-LLM.md` reference, which catalogues prompt-injection patterns and is the closest thing to a detection guide for the agent.
